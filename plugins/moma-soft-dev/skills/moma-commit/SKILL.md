# /moma-commit —— 未提交变更整理与规范提交

项目周期外的实用指令：一键区分工作区里混杂的未提交变更，把有用的改动按意图分组做成规范提交，把噪音（空文件、应忽略的产物、敏感文件）挡在提交之外，并在结束时提醒用户手动清理。

> 共享约定见 `${CLAUDE_PLUGIN_ROOT}/skills/moma-soft-dev/references/common-conventions.md`。本指令为项目周期外的实用指令，不依赖 01~09 文档，不做文档预检。

## 上下文范围

仅加载：git 工作区状态（已暂存 / 未暂存 / 未跟踪）、各变更的差异内容、现有 `.gitignore`、近期提交历史（用于探测提交信息风格）、花名册 `<docs-root>/.moma-state/roster.md`（仅多会话场景）。不加载插件内置模板，不加载 01~09 文档正文（若某个被变更的文件本身是文档，只读取其差异内容用于分组判断）。

## 步骤

1. **前置检查**
   - 当前目录必须是 git 仓库，否则中止并告知用户先初始化版本控制；
   - 检测是否存在进行中的合并/变基等未解决冲突状态：有则中止，提示用户先解决冲突再运行本指令；
   - 工作区完全干净（无已暂存、未暂存、未跟踪内容）时，报告"没有需要处理的变更"并结束；
   - 多会话模式（花名册中存在其他"进行中"条目）：按共享约定登记本会话条目（指令 `/moma-commit`，工作范围在第 3 步得出后再写入）。**本指令的职责就是整理未提交变更，因此不执行规则5的"前置检查点提交"**（检查点会把待分类内容整体吞掉，与本指令目的冲突）。

2. **收集并分类变更**
   列出全部已暂存、未暂存、未跟踪的文件（未跟踪目录展开到文件级），逐个归入四类：

   | 类别 | 判定标准 | 处理方式 |
   |------|----------|----------|
   | A 有用的改动 | 有实质内容的代码、文档、配置等变更 | 分组提交（步骤3） |
   | B 应被版本控制忽略的文件 | 构建产物（`dist/`、`build/`、`out/`、`__pycache__/`、`*.pyc`、`target/` 等）、依赖目录（`node_modules/` 等）、日志（`*.log`）、本地环境配置（`.env.local`、`*.local`）、IDE/编辑器配置（`.idea/`、`.vscode/`、`*.swp`）、操作系统临时文件（`.DS_Store`、`Thumbs.db`）、moma 会话状态目录 `.moma-state/` 等 | 不提交；生成 `.gitignore` 补充建议 |
   | C 无意义文件 | 零字节或仅含空白字符的文件、明显的无用临时文件（`*.tmp`、`*~`、随手命名的 `Untitled.*`、`新建文本文档.txt` 之类） | 不提交也不删除；结束时列出清单提醒用户手动清除 |
   | D 疑似敏感文件 | 疑似包含凭据或私钥的文件：`.env`、`*.pem`、`*.key`、`id_rsa`，或差异内容中出现密钥、Token、口令等高熵字符串 | 永不提交；醒目警告 |

   - **空文件白名单**：`__init__.py`、`.gitkeep`、`.keep`、`LICENSE` 等空文件具有明确用途，一律归入 A 类，不得判为 C 类。
   - **已被跟踪的 B 类文件**：若某 B 类文件已被 git 跟踪且本次是人为的正当修改（而非重新生成的产物），按 A 类处理。
   - **拿不准时**：无法确定归属的文件标注"待用户判断"，列入报告由用户在步骤4裁定，不得自作主张。

3. **为 A 类改动分组并生成提交计划**
   - **提交信息风格**：先探测近期提交历史的既有风格（语言、前缀约定），项目已有明确约定则沿用；否则采用 moma 系约定 `类型(范围): 中文描述`，类型取：`feat` 新功能 / `bug` 缺陷修复 / `optimize` 优化细化 / `modify` 需求调整 / `refactor` 重构 / `test` 测试 / `docs` 文档 / `chore` 杂务（配置、忽略规则等）/ `security` 安全 / `migrate` 数据迁移。
   - **分组原则（一个意图一个提交）**：
     1. 属于同一功能/修复的相关改动归为一组（通常集中在相同或关联的模块）；
     2. 代码改动与文档改动分开成组；锁文件（`package-lock.json`、`poetry.lock` 等）并入其依赖变更所在组；
     3. 明显不相关的改动（如功能甲 + 功能乙 + 顺手改的错别字）必须拆开；
     4. 同一文件内混杂多个意图时，尝试按差异块（hunk）分开暂存；无法可靠拆分时向用户说明，或将整个文件归入主要意图的组，由用户在步骤4裁定。
   - **多会话排除**：花名册中存在其他"进行中"会话时，位于其声明工作范围内的文件默认不纳入任何提交组，单独列为"其他会话进行中范围内的文件（本次不提交）"告知用户；用户明确确认后方可提交。
   - 产出**提交计划**：每个提交组的文件清单、提交信息、分组理由；连同 B 类清单及对应的 `.gitignore` 补充建议、C 类清单、D 类警告一起呈现。

4. **呈现计划并获用户确认**
   - 向用户呈现完整分类报告与提交计划，用户可：调整分组、移动或剔除文件、采纳/放弃 `.gitignore` 建议、中止全部操作；
   - **未获用户明确确认前不得执行任何提交**。若分析前已有用户手动暂存的内容，在报告中体现其原暂存状态；用户要求"已暂存部分保持原样作为单独一个提交"时照办。

5. **执行提交**
   - 严格按确认后的计划逐文件（或按差异块）暂存，**禁止一次性暂存整个工作区**；
   - 用户采纳 `.gitignore` 建议时：先以**追加**方式补充规则（不改写已有规则），将 `.gitignore` 单独作为一个 `chore` 提交；B 类文件若已被 git 跟踪，需经用户确认后将其移出跟踪（保留本地文件）；
   - 逐组创建提交；多会话模式下提交信息携带本会话 ID；
   - D 类文件不得进入任何提交；
   - 本指令不推送远端；如需推送由用户自行操作。

6. **结束报告与清理提醒**
   - 输出：本次生成的提交清单（提交信息与涉及文件）、工作区中剩余未处理的内容；
   - **提醒用户手动清除 C 类无意义文件**：给出文件清单与参考删除命令，但本指令绝不代为删除；
   - B 类文件若本次未采纳忽略规则，提醒其会反复出现在变更列表中，建议后续处理；D 类文件再次警告，建议改用环境变量或密钥管理方案并加入忽略规则；
   - 多会话模式：将花名册中本会话状态改为"已完成"。

## 纪律

- 本指令不修改任何业务代码与文档内容（唯一例外是经用户确认后追加 `.gitignore` 规则），只做分类、暂存与提交；
- 永不删除任何文件，无意义文件一律留给用户手动清除；
- 永不提交疑似敏感文件，永不推送远端；
- 所有提交都必须先经过用户确认，不得静默执行。
