# /moma-test —— 测试验证

依据测试策略文档补齐测试、执行测试、记录结果，并完成缺陷状态闭环（待修复 → 已修复 → 已验证）。

> 共享约定见 `${CLAUDE_PLUGIN_ROOT}/skills/moma-soft-dev/references/common-conventions.md`，编码通用约束（含验证阶梯）必须严格遵守——测试代码也是代码。本文件中 `dev-docs/` 路径均遵循共享约定的文档存放规则。

## 上下文范围

加载 `dev-docs/07-测试策略.md`（测试层次、优先级、用例设计、Mock 策略）+ `dev-docs/02-产品需求文档.md`（验收标准）+ `dev-docs/05-API接口文档.md`（接口契约）+ `dev-docs/06-开发规约.md`（测试代码规范）+ `dev-docs/09-BUG记录.md`（如存在，用于回归验证）+ 被测功能的相关业务代码（只读）。不加载 01/03/04（除非测试涉及架构或数据约束），不加载插件内置模板。

## 步骤

1. **文档预检、登记与检查点**
   - 按共享约定"文档预检规则"检查 `07-测试策略.md`：缺失则中止，提示用户先执行 `/moma-init`（新项目）或 `/moma-sync`（已有代码）生成文档。
   - 按"多会话并行规约"生成会话 ID，读取花名册 `<docs-root>/.moma-state/roster.md`（不存在则创建）：工作范围声明为测试代码文件/目录（如 `tests/`、`src/**/__tests__/`、`*_test.go` 等）+ `<docs-root>/test-reports/` + `09-BUG记录.md`（如需登记缺陷）。范围重叠时拒绝直接执行并报告冲突，按"规则6：worktree 兜底隔离"提议迁移，获用户确认后在 worktree 内执行；否则调整范围或等待。若无重叠，登记本会话条目（状态"进行中"）。
   - 若工作区存在未提交改动，先按规则5生成 `checkpoint:` 提交。
2. **盘点测试现状**：清点已有测试文件与测试执行方式（从依赖/构建清单读取测试命令）；对照 07 的用例设计与 02 的功能点、05 的接口，列出未覆盖的场景。
3. **补齐测试代码**：按 07 的测试层次（单元/集成/E2E）与优先级（P0 优先）补齐缺失用例，覆盖正向、反向、边界、异常场景；测试代码遵循 `⚠️ AI 约束` 与 06 规约。**不得修改业务代码**——怀疑业务代码有缺陷时按步骤6登记。
4. **执行测试**：使用项目自身的测试命令（如 `npm test`、`pytest`、`mvn test`、`go test ./...`）执行，收集通过/失败/跳过数量与失败详情。若环境无法执行测试，如实报告原因，降级为用例静态评审并说明。
5. **写入测试报告**：在 `<docs-root>/test-reports/`（不存在则创建）新建 `test-report-YYYYMMDD-HHmm.md`，使用文末模板。
6. **缺陷登记与回归闭环**：
   - 失败用例若判定为业务代码缺陷：按 `dev-docs/07-测试策略.md` "6.2 缺陷记录模板"以追加式写入规则登记到 `dev-docs/09-BUG记录.md`（编号取当前最大 BUG 编号加 1，条目含会话 ID，状态置"待修复"），建议用户执行 `/moma-fix`；不直接修改业务代码。
   - 对 09 中状态为"已修复"的条目：优先补跑或补写对应回归用例；通过则按共享约定规则4的"状态流转例外"将状态改为"已验证"并追加状态备注；不通过则改回"待修复"并注明原因。
7. **提交**：如果项目有版本控制，生成 `test: <测试简述>` 格式的提交：只暂存本会话工作范围内的文件（测试代码、测试报告、09），提交信息携带会话 ID。
8. **收尾**：将花名册中本会话状态改为"已完成"；向用户报告通过率、新增缺陷数、回归验证结果与建议的下一步（如 `/moma-fix`、`/moma-review`）。
