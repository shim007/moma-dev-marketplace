# moma-* 系列共享约定

本文件被所有 `moma-*` 子 skill 引用，集中维护文档路径、文档体系与编码通用约束。

## 文档存放规则

项目文档默认存放在工作目录的 `dev-docs/` 文件夹中，其次是 `docs/`。

- **查找文档：** 优先在 `dev-docs/` 下查找，找不到再在 `docs/` 下查找。
- **创建/更新文档：** 优先写入 `dev-docs/`（不存在则创建该目录）；只有当当前项目仅存在 `docs/` 而无 `dev-docs/` 时，才继续使用 `docs/`。
- **会话归档目录：** `<docs-root>/session-records/`，与上面的 `<docs-root>` 保持一致。

模板文件统一来自插件内置模板目录 `${CLAUDE_PLUGIN_ROOT}/templates/simple-software/`。

> `${CLAUDE_PLUGIN_ROOT}` 在 Claude Code / GitHub Copilot CLI 中会自动解析为本插件的安装根目录；在其他 AI 工具中可能不会展开，此时请将其理解为"本插件所在目录的绝对路径"（即安装或手动拷贝 `moma-soft-dev` 插件目录的位置），再据此定位文件。

> 各 `moma-*` skill 中出现的 `docs/` 路径均遵循上述查找/创建规则，实际优先使用 `dev-docs/`。

## 文档体系与阶段

- **阶段1 — 需求定义：** `01-项目概要.md`、`02-产品需求文档.md`
- **阶段2 — 技术设计：** `03-技术架构文档.md`、`04-数据模型文档.md`、`05-API接口文档.md`
- **阶段3 — 开发约束：** `06-开发规约.md`、`07-测试策略.md`
- **阶段4 — AI 编码：** 参照 01~07 全部文档进行编码实现
- **贯穿全流程：** `08-变更日志.md`
- **缺陷跟踪：** `09-BUG记录.md`

文档间依赖关系详见 `doc-dependencies.md`。

## 编码通用约束

适用于所有涉及代码变更的指令（`/moma-coding`、`/moma-modify`、`/moma-optimize`、`/moma-new`、`/moma-fix`、`/moma-test`）：

1. **约束即法律：** 文档中的 `⚠️ AI 约束` 标记具有最高优先级，编码时不得违反。
2. **可追溯性：** 代码实现必须能追溯到需求文档中的具体条目。
3. **先登记后变更：** 如需偏离文档，必须先更新 `08-变更日志.md`，获用户确认后再执行。
4. **自我验证：** 实现后按下列"验证阶梯"验证，全部通过才算阶段完成。
5. **验证阶梯：** "自我验证"至少按技术栈依次完成以下检查，任一层级失败应立即停止并修复，不得跳过：
   1. **静态检查：** 编译/构建通过；项目配置了 lint 时 lint 通过；
   2. **测试验证：** 既有测试全部执行且通过；项目尚无测试时，至少手动或脚本化验证核心路径可运行，并建议后续 `/moma-test` 补齐；
   3. **冒烟验证：** 程序可启动，或目标功能/接口可调用且主要输入输出符合 02/05 文档描述。
   深度测试覆盖与回归验证交由 `/moma-test` 承担。

## 文档预检规则

依赖 01~07 文档的指令（`/moma-coding`、`/moma-modify`、`/moma-optimize`、`/moma-new`、`/moma-fix`、`/moma-test`、`/moma-review`、`/moma-check`、`/moma-release`）执行前，必须先按"文档存放规则"定位 `<docs-root>`，并检查阶段1文档（`01-项目概要.md` 或 `02-产品需求文档.md`）是否存在：

- **`<docs-root>` 不存在或阶段1文档缺失：** 中止本次执行并路由——无代码的新项目建议先执行 `/moma-init`；已有代码的项目建议先执行 `/moma-sync`。不得在无约束文档的情况下进入编码或变更。
- **仅部分文档缺失**（如有 01/02 但缺 03~07 中的某几份）：可继续执行，但必须向用户明确指出缺失的文档及其影响（如"缺少 07-测试策略，本次无法验证测试要求"），不得静默视为无约束。
- **例外——`/moma-fix`：** 修复线上或紧急缺陷不应被文档缺失阻塞。文档缺失时告知用户后跳过依赖文档的步骤（约束核对、07 缺陷模板），继续完成定位与修复，缺陷记录使用 `/moma-fix` 技能内置模板，并建议事后 `/moma-sync` 补齐文档。
- **例外——`/moma-review`：** 文档缺失时降级为通用工程评审（见该技能说明），不中止。

## 上下文精简原则

每个 `moma-*` 子 skill 只加载其明确列出的"上下文范围"中的文档和代码：

- 避免无关文档干扰 AI 的判断，降低噪音
- 确保 AI 聚焦于当前任务最相关的信息
- 对于所需文档，也只关注与当前操作相关的章节，跳过无关内容

## 多会话并行规约

moma-* 工作指令支持多个 AI 会话（agent）在同一工作目录下并行执行。并行安全基于以下六条规则，所有工作指令开工前必须遵守。当花名册中没有其他"进行中"条目时（单会话模式），并行限制全部不生效，行为与旧版本一致。

### 规则1：会话 ID 与花名册登记

- 每个会话在执行第一个工作指令前，生成唯一的**会话 ID**，格式 `S-MMDD-HHmm-<短词>`（如 `S-0808-1430-auth`），全程使用。
- 花名册文件为 `<docs-root>/.moma-state/roster.md`（`<docs-root>` 遵循上文的文档存放规则；文件或目录不存在则创建），格式：

  ```markdown
  | 会话 ID | 指令 | 工作范围 | 状态 | 开始时间 | 最后活跃 |
  |---------|------|----------|------|----------|----------|
  | S-0808-1430-auth | /moma-coding | src/auth/ | 进行中 | 08-08 14:30 | 08-08 15:10 |
  ```

- 任何工作指令执行前：读取花名册 → 登记本会话条目（状态"进行中"）→ 再开始工作；指令完成后将状态改为"已完成"（保留条目，便于追溯）。
- **陈旧条目**：某条目"最后活跃"超过 2 小时未更新，后续会话可判定其为残留，备注说明后继续执行，不要静默删除条目。
- `<docs-root>/.moma-state/` 属于本地会话状态，建议在项目版本控制中忽略。

### 规则2：工作范围与代码并行

- 涉及代码修改的指令（`/moma-coding`、`/moma-modify`、`/moma-optimize`、`/moma-new`、`/moma-fix`、`/moma-test`、`/moma-release`）登记时必须在花名册中声明**工作范围**：本次将修改的具体文件/目录（如 `src/auth/`、`src/api/user.ts`），尽量具体；无法预先确定时，先分析代码确定范围，再登记，再动手。
- 只读或仅产出独立记录文件的指令（`/moma-check`、`/moma-review`）不声明代码工作范围，不参与范围冲突判定，可与其他指令并行。
- 登记时与花名册中其他"进行中"条目的工作范围比对：**存在重叠则拒绝执行**，并告知用户与哪个会话冲突、其范围是什么，由用户调整本会话范围或等待对方完成。
- 任务横跨整个项目（如首次实现）时，范围声明为"全项目"，自然与其他会话互斥。

### 规则3：文档单写者

- 01~07 文档是共享的编码约束，**同一时刻只允许一个"进行中"会话写入**。
- 写入任一 01~07 文档前检查花名册：若其他"进行中"会话的工作范围包含任何 01~07 文档，则拒绝本次文档写入（不影响无关的代码写入）并向用户报告。
- **独占指令**：`/moma-init` 与 `/moma-sync` 生成整套文档，花名册中存在任何其他"进行中"条目（无论范围）时拒绝执行。
- **写前重确认**：对 01~07 的任何写入，落笔前重新读取该文件一次；若内容与上次读取不同（被其他会话修改过），停止并基于最新内容重新规划，不得基于过时上下文覆盖。

### 规则4：追加式写入（08-变更日志、09-BUG记录）

- 08 与 09 只允许在末尾**追加**新条目，禁止修改、删除或重排已有内容。
- 写入流程：
  1. 重新读取目标文件全文；
  2. 以当前最大编号（CR-/BUG-）加 1 作为新条目编号；
  3. 追加条目，**条目中必须包含会话 ID**；
  4. 写入后重读验证：自己的条目完整、已有条目无损；发现异常则从 git 检查点恢复后重试；发现编号冲突则重新编号。
- **例外：状态流转的受控更新。** 08 CR 条目与 09 BUG 条目中的"状态"字段（如 待修复 → 修复中 → 已修复 → 已验证）天然需要流转，允许受控更新，但必须同时满足：
  1. 只允许改动该条目内的"状态"一行，条目的其余内容与所有其他条目一律不得改动；
  2. 在该条目末尾追加一行状态备注：`> 状态备注：<旧状态> → <新状态>（会话 <会话 ID>，<时间>）`；
  3. 写入前后重读验证，流程同上。
  典型流转：`/moma-fix` 修复后将 BUG 状态置为"已修复"；`/moma-test` 回归通过后流转为"已验证"，不通过则改回"待修复"。除状态字段外，08 与 09 仍严格只允许追加。

### 规则5：git 检查点与范围提交

- 执行涉及代码修改的指令前，若工作区存在未提交改动，先生成 `checkpoint: <会话 ID> <指令>前` 提交（可能包含多个会话的文件，仅用于回滚保障）。
- 指令完成后生成提交时，**只暂存本会话声明的工作范围内的文件**，禁止暂存整个工作区；提交信息中包含会话 ID。
- 项目无版本控制时跳过本规则，并在高危操作前建议用户手动备份。

### 规则6：worktree 兜底隔离

当规则2、规则3与独占指令的冲突无法避免时，可将"拒绝并等待"升级为"迁移到独立 git worktree 继续"，把实时冲突转化为合并时的显式冲突。

**触发时机**（即上述三个冲突点）：

- 登记时工作范围与其他"进行中"会话重叠；
- 需要写入 01~07 文档但另一会话正在写文档；
- 执行独占指令（`/moma-init`、`/moma-sync`）时存在其他活跃会话。

**流程**：

1. **提议**：向用户报告冲突并提议 worktree 隔离，给出计划的 worktree 路径（建议 `../<项目名>-<会话 ID>`）与分支名（建议 `moma/<会话 ID>`），并说明代价：额外磁盘占用、构建依赖（如 node_modules）不共享需重新安装等。**必须获得用户确认后才执行**；用户也可通过指令预先授权自动执行。
2. **前置检查**（任一不满足则放弃隔离，退回"等待对方会话完成或调整本会话范围"）：
   - 项目是 git 仓库；
   - `<docs-root>` 已纳入版本控制（否则 worktree 中没有文档，moma 流程失去约束依据）；
   - 当前仓库状态允许创建 worktree。
3. **创建**：基于主工作目录当前分支的最新提交创建新分支并检出到 worktree。
4. **登记标注**：在主目录花名册中将本会话条目备注"已迁移至 worktree `<路径>`，不再占用主目录范围"；在 worktree 内新建花名册并登记本会话。
5. **继续工作**：该会话在 worktree 内继续执行完整 moma 流程（本文全部规则在 worktree 内照常适用）。
6. **合并回主分支**：工作完成后，建议用户将 worktree 分支合并回主分支。无冲突即完成；有冲突时以显式 git 冲突呈现，按文档约定解决（合并后的文档需重新检查内部一致性及其与代码的一致性），不得静默丢弃任何一方的变更。

**迁移时机**：迁移适合发生在指令开始时。执行中途发现需要触碰其他会话的范围时，应先完成当前最小步骤并提交，再重新登记或按本规则迁移。

### 确认与报告

多会话场景下，所有需要用户确认的请求、冲突报告与产出说明都必须携带会话 ID，确保用户能区分对应的是哪个会话。

## 指令一览

| 指令 | 用途 |
|------|------|
| `/moma-init` | 启动新项目，生成全套文档 |
| `/moma-sync` | 分析已有项目代码，补全或生成文档 |
| `/moma-coding` | 文档就绪后进入编码 |
| `/moma-modify` | 调整已有需求，同步文档与代码 |
| `/moma-optimize` | 对已有功能进行细节约束优化（含纯重构模式） |
| `/moma-new` | 增加原需求未包含的新功能 |
| `/moma-fix` | 定位并修复代码异常 |
| `/moma-test` | 补齐并执行测试，输出报告，闭环缺陷状态 |
| `/moma-review` | 对照文档与规约评审代码变更，输出分级问题 |
| `/moma-check` | 只读检查文档与代码的双向漂移（防腐层） |
| `/moma-release` | 聚合变更记录，产出发布说明、版本号与 tag |
| `/moma-session-complete` | 总结当前会话流程并归档为 md 文档 |
