# moma-* 变更指令通用流程

本文件是 `/moma-modify`、`/moma-optimize`、`/moma-new` 三个变更指令的共享执行流程，集中于此维护，避免三份 SKILL.md 重复同一流程导致漂移。三个指令仅在"变更意图判断"、"提交前缀"与"个别高危规则"上不同，其余步骤一律以本文件为准。

> 修改本文件时，必须同步检查三个指令的 SKILL.md、`common-conventions.md` 与 `evals/evals.json`。

## 步骤1：文档预检、登记与检查点

1. 按 `common-conventions.md` 的"文档预检规则"检查文档：`<docs-root>` 或阶段1文档缺失时，按该规则路由（`/moma-init` 或 `/moma-sync`）并中止本次执行。
2. 按"多会话并行规约"生成会话 ID，读取花名册 `<docs-root>/.moma-state/roster.md`（不存在则创建）：
   - 工作范围声明为：本次将更新的 01/02 及下游文档 + 将变更的代码文件；
   - 若与其他"进行中"会话的工作范围重叠，拒绝直接执行并报告冲突，按"规则6：worktree 兜底隔离"提议迁移到独立 worktree 继续，获用户确认后在 worktree 内执行；若用户不接受或前置检查不满足，则调整本会话范围或等待对方完成；
   - 若无重叠，登记本会话条目（状态"进行中"）。
3. 若工作区存在未提交改动，先按规则5生成 `checkpoint:` 提交。

## 步骤2：变更意图分析

结合 `01-项目概要.md` 与 `02-产品需求文档.md`，分析用户输入，明确变更点、归属模块与受影响的下游文档（判断范围参照 `doc-dependencies.md` 的"变更影响分析"）。

各指令的判断侧重点见其 SKILL.md 的"本指令判定点"。

## 步骤3：同步更新文档

更新阶段1文档，并同步更新受影响的下游文档（03~07 中相关部分）。遵循"文档单写者"规则：

- 写入每个文档前先重新读取确认；若发现被其他会话修改，则基于最新内容重新规划，不得基于过时上下文覆盖；
- 若有其他会话正在写文档，则拒绝本次文档写入并报告，可提议按规则6迁移（剩余步骤在 worktree 内完成）或等待对方完成；
- 如果下游文档已存在，必须逐一检查并更新；如果尚未生成则跳过。

**例外：** `/moma-optimize` 的纯重构模式跳过本步骤（见该指令 SKILL.md）。

**迁移路由：** 若变更涉及 `04-数据模型文档.md` 的**实际结构变更且需要数据迁移**（删列、类型变更、数据回填等高危操作），文档更新完成后应建议用户改用 `/moma-migrate` 执行迁移（可回滚、先备份、确认后执行），不要在普通变更流程中直接修改生产数据结构。

## 步骤4：代码变更

根据变更需求进行代码变更，严格遵循 `⚠️ AI 约束` 标记，并按共享约定"验证阶梯"完成自我验证。期间生成提交时只暂存本会话工作范围内的文件，提交信息携带会话 ID。

## 步骤5：登记变更日志

按追加式写入规则在 `dev-docs/08-变更日志.md` 中记录本次变更（编号取当前最大 CR 编号加 1，条目含会话 ID；文件不存在则创建）。"变更类型"字段按变更性质填写（需求变更 / 设计变更 / 技术变更 / 缺陷修复）。

## 步骤6：生成提交

如果项目有版本控制，按指令声明的前缀（`modify:` / `optimize:` / `feat:`）生成提交：**只暂存本会话工作范围内的文件**，提交信息携带会话 ID。

## 步骤7：收尾

1. 将花名册中本会话状态改为"已完成"。
2. 向用户简要汇报：变更点、更新的文档清单、代码变更与提交信息、建议的下一步（如 `/moma-test` 验证、`/moma-review` 评审）。
