# /moma-review —— 代码评审

以文档为评审基准，检查代码变更是否满足需求、遵守约束、符合规约，并给出分级问题清单。

> 共享约定见 `${CLAUDE_PLUGIN_ROOT}/skills/moma-soft-dev/references/common-conventions.md`。本文件中 `docs/` 路径均遵循共享约定的 `dev-docs/` 优先规则。

## 上下文范围

加载评审范围内的代码变更 + `docs/02-产品需求文档.md`（需求追溯与验收标准）+ `docs/03-技术架构文档.md`（架构与技术栈约束）+ `docs/06-开发规约.md`（编码规范）+ `docs/07-测试策略.md`（测试要求）+ 上述文档中全部 `⚠️ AI 约束` 标记。不加载 01/04/05（除非变更直接涉及范围、数据模型或接口契约），不加载插件内置模板。

## 步骤

1. **登记**
   - 按"多会话并行规约"生成会话 ID，读取花名册 `<docs-root>/.moma-state/roster.md`（不存在则创建），登记本会话条目（指令 `/moma-review`、工作范围"只读评审 + review-records/"、状态"进行中"）。
   - 本指令只读代码、只新增评审记录文件，不构成代码工作范围冲突，可与其他指令并行执行；无需 checkpoint 提交。
2. **确定评审范围**：
   - 用户指定了文件/目录/提交范围时，以指定范围为准；
   - 未指定时，默认为当前工作区未提交的改动（git diff）与当前分支未推送的提交；两者皆无则询问用户。
3. **文档预检**：按共享约定"文档预检规则"检查文档；文档缺失时不中止，降级为通用工程评审（正确性、安全、可维护性），并在报告中明确注明"无文档约束可对照"。
4. **按维度评审**：
   - **需求符合性**：实现是否覆盖对应需求条目（可追溯性）；是否存在无需求依据的额外功能（需求外代码）；
   - **约束符合性**：逐条对照相关 `⚠️ AI 约束` 标记；
   - **架构符合性**：分层、依赖方向、技术选型是否符合 03，有无技术栈漂移；
   - **规约符合性**：命名、结构、错误处理等是否符合 06；
   - **正确性与安全**：边界条件、异常处理、注入、越权、敏感信息、并发问题；
   - **测试充分性**：关键变更是否有对应测试（对照 07 的层次与 P0 要求）。
5. **问题分级**：每个问题必须包含位置（文件/行）、描述、违反的约束或规约条目、修复建议。
   - **阻断**：违反 `⚠️ AI 约束`、功能性错误、安全漏洞——必须修复后方可合并；
   - **严重**：高概率引发故障或明显偏离需求；
   - **一般**：规约不符、可维护性问题；
   - **建议**：优化方向，不强制。
6. **写入评审记录**：在 `<docs-root>/review-records/`（不存在则创建）新建 `review-YYYYMMDD-HHmm.md`，使用文末模板，并向用户输出问题清单摘要。
7. **缺陷登记（可选）**：阻断级且构成功能缺陷的问题，经用户确认后按 `07-测试策略.md` "6.2 缺陷记录模板"以追加式写入规则登记到 `docs/09-BUG记录.md`（状态"待修复"，条目含会话 ID）。
8. **结论与收尾**：给出结论——通过（可合并）/ 有条件通过（仅一般、建议项）/ 不通过（存在阻断或严重项）；将花名册中本会话状态改为"已完成"，并建议下一步（不通过项交 `/moma-fix` 或直接修复，修复后重新 `/moma-review`）。

## 评审记录模板

```markdown
# 代码评审记录 {{YYYY-MM-DD HH:mm}}

- **会话 ID：** {{会话 ID}}
- **评审范围：** {{文件列表 / 提交范围 / git diff}}
- **评审基准：** 02/03/06/07 及 ⚠️ AI 约束（文档缺失时注明"通用工程评审"）

## 问题清单

### [{{阻断/严重/一般/建议}}] {{问题标题}}
- **位置：** {{文件:行号}}
- **描述：**
- **违反的约束/规约：** {{⚠️ AI 约束原文或 06 规约条目；无则写"工程最佳实践"}}
- **修复建议：**

## 结论

- [ ] 通过（可合并）
- [ ] 有条件通过（仅一般/建议项）
- [ ] 不通过（存在阻断/严重项，修复后需重新评审）
```

此指令不直接修改业务代码；发现问题后由用户决定交 `/moma-fix` 处理或自行修复。
