# /moma-migrate —— 数据库迁移

数据模型变更的专用高危流程：文档先行、脚本可回滚、备份前置、确认后执行。适用于删列/改类型/数据回填等直接改 `/moma-modify` 代码风险过高的场景。

> 共享约定见 `${CLAUDE_PLUGIN_ROOT}/skills/moma-soft-dev/references/common-conventions.md`。本文件中 `docs/` 路径均遵循共享约定的 `dev-docs/` 优先规则。

## 上下文范围

加载用户的迁移诉求 + `docs/04-数据模型文档.md` + `docs/03-技术架构文档.md`（数据库类型与约束）+ `docs/06-开发规约.md`（模型与迁移代码规范）+ 项目现有迁移文件、ORM 模型与 DAO 层代码 + `docs/08-变更日志.md`。不加载无关文档。

## 步骤

1. **文档预检、登记与检查点**
   - 按共享约定"文档预检规则"检查：阶段1文档缺失则中止并路由；01/02 存在但 `04-数据模型文档.md` 缺失时，先建议补齐 04（`/moma-sync` 或基于代码整理），再继续。
   - 按"多会话并行规约"生成会话 ID，读取花名册：工作范围声明为 04 文档 + 迁移脚本目录 + 本次迁移涉及的模型/DAO 代码；冲突处理遵循规则2与规则6。若无重叠，登记本会话条目（状态"进行中"）。
   - 若工作区存在未提交改动，先按规则5生成 `checkpoint:` 提交。
2. **变更分析**：对比目标模型与现状，逐项列出变更（增/删表、增/删列、类型变更、索引与约束变更、数据回填），并评估每项风险：
   - **高危**：删列、删表、类型收窄（如长度缩短、大类型改小类型）、对存量数据加非空约束、大规模数据改写；
   - **中危**：大表加索引（锁表风险）、表/列重命名；
   - **低危**：新增可空列/表、删减索引。
3. **更新文档**：遵循"文档单写者"规则同步更新 `docs/04-数据模型文档.md`（写前重读确认）；按追加式写入规则在 `docs/08-变更日志.md` 登记 CR 条目（变更类型"数据模型变更"，列出受影响表与风险等级，条目含会话 ID；文件不存在则创建）。
4. **生成迁移脚本**：
   - 优先使用项目已有的迁移工具（Flyway / Liquibase / Alembic / Prisma / knex migrations 等），遵循其命名与目录约定；项目无迁移工具时生成 SQL 脚本，并建议引入迁移机制；
   - **每个迁移脚本必须配套回滚脚本或回滚说明**；高危变更默认拆分为多个小步骤，每步可独立回滚；
   - 删列/删表默认**两阶段执行**：第一阶段重命名为 `__deprecated_` 前缀保留观察，第二阶段经用户确认后再物理删除；
   - 同步更新受影响的模型/DAO 代码，遵循 `⚠️ AI 约束` 与 06 规约。
5. **备份与授权**：执行前确认目标库或受影响表已完成备份（给出备份命令或工具用法并向用户确认已执行）；**物理删除任何数据必须获得用户明确确认**，默认永不物理删除。
6. **执行与验证**：
   - 先在测试环境或 dry-run 执行；两者皆不可用时，逐条展示迁移与回滚脚本内容供用户人工审查后再继续；
   - 生产/目标环境的正式执行必须**逐项获得用户确认**——AI 准备好命令，由用户执行或明确授权后执行；
   - 执行后验证：抽查数据完整性（行数、关键字段、外键一致性），确认应用可启动、相关功能可用，建议交 `/moma-test` 做回归。
7. **提交**：生成 `migrate: <迁移简述>` 格式的提交：只暂存本会话工作范围内的文件（迁移脚本、模型代码、04 文档、08），提交信息携带会话 ID。
8. **收尾**：将花名册中本会话状态改为"已完成"；报告执行结果、回滚方案存放位置与建议观察期（高危变更建议明确观察窗口，期间不做后续结构变更）。

此指令的核心纪律：**可回滚、先备份、用户逐项确认**——任何一步缺失都应停止并向用户报告。
