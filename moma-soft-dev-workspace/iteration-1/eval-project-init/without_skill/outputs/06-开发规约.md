## 2. 通用编码规范

### 2.1 命名规范

> **⚠️ AI 约束：以下命名规范是强制性的，AI 不得使用其他命名风格。**

| 元素 | 规范 | 示例 |
|------|------|------|
| 项目/仓库名 | kebab-case | `campus-trade` |
| 前端文件名 | PascalCase（组件）/ camelCase（工具） | `ProductCard.tsx` / `formatDate.ts` |
| 后端文件名 | PascalCase | `ProductService.java` |
| 类名 | PascalCase | `UserService`, `ProductController` |
| 函数/方法名 | camelCase | `getUserById`, `createOrder` |
| 变量名 | camelCase | `currentUser`, `productList` |
| 常量名 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT`, `DEFAULT_PAGE_SIZE` |
| 数据库表名 | snake_case | `trade_order`, `product_image` |
| 数据库字段名 | snake_case | `seller_id`, `created_at` |
| API 路径 | kebab-case | `/api/v1/pickup-points` |
| 环境变量 | UPPER_SNAKE_CASE | `DATABASE_URL`, `JWT_SECRET` |
| React 组件 | PascalCase | `<ProductList />`, `<ChatWindow />` |
| React Hooks | camelCase，use 前缀 | `useAuth`, `useProducts` |
| TypeScript 接口/类型 | PascalCase，I 前缀（接口可选） | `Product`, `UserResponse` |

### 2.2 代码风格

**前端（TypeScript/React）：**
- 缩进：2 空格
- 行宽限制：120 字符
- 引号风格：单引号
- 分号：必须使用分号
- 组件文件使用 `.tsx` 扩展名，纯逻辑文件使用 `.ts`

**后端（Java/Spring Boot）：**
- 缩进：4 空格
- 行宽限制：120 字符
- 大括号：K&R 风格（左括号不换行）
- 方法之间空一行

### 2.3 注释规范

**后端注释：**
- 类注释使用 Javadoc 格式，包含类描述和 `@author`
- 公共方法使用 Javadoc 格式，包含 `@param` 和 `@return`
- 复杂业务逻辑需要行内注释说明原因

**前端注释：**
- 组件文件顶部使用 JSDoc 注释说明组件用途
- 公共工具函数使用 JSDoc 注释，包含参数和返回值说明
- 复杂状态管理逻辑需要注释

**AI 特别约束：**
- ✅ 复杂业务逻辑必须添加注释
- ✅ 公共 API/函数必须有文档注释
- ❌ 禁止无意义的注释（如 `// 设置名字` `this.name = name`）
- ❌ 禁止注释掉的代码提交

## 3. 架构规范

### 3.1 分层职责

> **⚠️ AI 约束：严格遵守分层架构，不得跨层调用。**

| 层级 | 职责 | 可以调用 | 不可调用 |
|------|------|----------|----------|
| Controller | 接收请求、参数校验、返回响应 | Service | Mapper、直接操作数据库 |
| Service | 业务逻辑实现、事务管理 | Mapper、其他 Service | Controller |
| Mapper | 数据库操作 | - | Service、Controller |
| DTO | 数据传输对象（请求/响应） | - | 不包含业务逻辑 |
| Entity | 数据库映射实体 | - | 不包含业务逻辑 |

**前端分层：**

| 层级 | 职责 | 可以调用 | 不可调用 |
|------|------|----------|----------|
| Pages | 页面组件、路由入口 | Components、Hooks、Store、API | 直接操作 DOM |
| Components | 可复用 UI 组件 | Hooks、工具函数 | API（通过 props 或 hooks） |
| Hooks | 自定义逻辑封装 | Store、API、工具函数 | 直接操作 DOM |
| Store | 全局状态管理 | API | 组件 |
| API | HTTP 请求封装 | Axios | 组件、Store |

### 3.2 模块通信规则

- 后端模块间通过 Service 层接口调用，禁止 Controller 间直接调用
- 前端模块间通过 Zustand Store 共享状态，或通过 Props 传递
- WebSocket 消息通过统一的消息处理器分发

## 4. 错误处理规范

> **⚠️ AI 约束：AI 编码时必须按以下规范处理错误，不得静默吞掉异常。**

### 4.1 错误处理原则

- **业务异常**：使用自定义 `BusinessException`，携带错误码和用户可读消息
- **系统异常**：捕获后记录详细日志，返回通用错误提示
- **参数校验异常**：使用 `@Valid` 注解，统一由全局异常处理器格式化
- **所有异常必须记录日志**，业务异常用 WARN，系统异常用 ERROR

### 4.2 统一异常结构

```java
/**
 * 业务异常
 */
public class BusinessException extends RuntimeException {
    private final String code;
    private final String message;

    public BusinessException(String code, String message) {
        super(message);
        this.code = code;
        this.message = message;
    }
}
```

### 4.3 日志规范

| 日志级别 | 使用场景 | 示例 |
|----------|----------|------|
| ERROR | 系统异常、第三方服务调用失败、数据库连接失败 | `数据库连接超时: {detail}` |
| WARN | 业务异常、参数校验失败、操作频率超限 | `用户登录失败，邮箱: a***@edu.cn` |
| INFO | 关键业务操作、状态变更 | `用户注册成功，ID: 1` |
| DEBUG | 方法调用详情、SQL 语句（仅开发环境） | `查询商品列表，参数: {params}` |

## 5. 安全编码规范

> **⚠️ AI 约束：以下安全规范为红线，违反任一条即视为严重缺陷。**

- [x] 所有用户输入必须校验和净化（使用 `@Valid` + 自定义校验器）
- [x] SQL 查询必须使用参数化查询（MyBatis-Plus 默认支持）
- [x] 敏感信息（密码、密钥）禁止硬编码，必须使用环境变量或配置文件
- [x] 密码存储必须使用 BCrypt 加盐哈希
- [x] API 必须有速率限制（登录接口 5 次/分钟，其他接口 60 次/分钟）
- [x] 文件上传必须校验类型和大小（白名单：jpg/jpeg/png/webp，≤5MB）
- [x] JWT Token 过期时间严格限制（Access 24h，Refresh 7d）
- [x] 前端输出必须进行 XSS 转义（React 默认转义，dangerouslySetInnerHTML 禁止使用）
- [x] CORS 配置仅允许指定域名访问
- [x] 日志中禁止记录完整邮箱和密码信息

## 6. 版本控制规范

### 6.1 分支策略

采用简化 Git Flow：

| 分支 | 用途 | 命名规范 |
|------|------|----------|
| main | 生产分支，始终可部署 | `main` |
| develop | 开发主分支 | `develop` |
| feature/* | 功能开发分支 | `feature/user-auth`, `feature/product-publish` |
| fix/* | 缺陷修复分支 | `fix/login-error` |
| release/* | 发布准备分支 | `release/v1.0` |

### 6.2 提交信息规范

> **⚠️ AI 约束：每次提交必须遵循以下格式。**

```
<type>(<scope>): <subject>

<body>

<footer>
```

**type 取值：**

| 类型 | 说明 |
|------|------|
| feat | 新功能 |
| fix | 修复缺陷 |
| docs | 文档变更 |
| style | 代码格式（不影响逻辑） |
| refactor | 重构 |
| test | 测试相关 |
| chore | 构建/工具变更 |

**scope 取值（与模块对应）：** user, product, chat, order, review, favorite, report, notification, common

**示例：** `feat(product): 实现商品发布接口`

## 7. 依赖管理规范

- **添加新依赖前**必须确认：
  - [ ] 该依赖在技术架构文档中已列出，或已获得确认更新架构文档
  - [ ] 许可证兼容性已确认（MIT/Apache 2.0 优先）
  - [ ] 无已知高危漏洞
- **禁止事项：**
  - ❌ 禁止引入与已有依赖功能重复的库
  - ❌ 禁止使用已废弃（deprecated）的库
  - ❌ 禁止锁定不明确的版本范围（如 `*` 或 `latest`）

## 8. 测试规范

### 8.1 测试要求

- 后端 Service 层单元测试覆盖率 ≥80%
- 所有 API 接口必须有集成测试
- 关键业务流程（注册→发布→交易→评价）必须有端到端测试

### 8.2 测试命名规范

- 后端测试类：`{ClassName}Test.java`（如 `ProductServiceTest.java`）
- 后端测试方法：`should_{预期行为}_when_{条件}`（如 `should_createProduct_when_validInput`）
- 前端测试文件：`{ComponentName}.test.tsx`（如 `ProductCard.test.tsx`）

### 8.3 测试目录结构

```
backend/src/test/java/com/campustrade/
├── user/
│   ├── controller/UserControllerTest.java
│   └── service/UserServiceTest.java
├── product/
│   ├── controller/ProductControllerTest.java
│   └── service/ProductServiceTest.java
├── ...

frontend/src/
├── pages/
│   ├── home/__tests__/HomePage.test.tsx
│   └── product/__tests__/ProductDetail.test.tsx
├── components/
│   └── common/__tests__/ProductCard.test.tsx
```

## 9. AI 编码专项约束

> **以下约束专门针对 AI 代码生成场景设计，防止 AI 常见的编码偏差。**

### 9.1 禁止行为清单

| 编号 | 禁止行为 | 说明 |
|------|----------|------|
| R-01 | 禁止自行添加需求文档中未定义的功能 | 防止范围蔓延 |
| R-02 | 禁止更换技术架构文档中确定的技术栈 | 保持技术一致性 |
| R-03 | 禁止添加数据模型文档中未定义的表和字段 | 保持数据结构一致 |
| R-04 | 禁止修改 API 文档中已定义的接口契约 | 保持接口稳定 |
| R-05 | 禁止使用 TypeScript `any` 类型 | 保证类型安全 |
| R-06 | 禁止在代码中硬编码配置值 | 使用配置文件/环境变量 |
| R-07 | 禁止忽略错误处理 | 所有错误必须捕获和处理 |
| R-08 | 禁止生成占位符代码（如 `// TODO: implement`） | 必须实现完整逻辑 |
| R-09 | 禁止使用 `dangerouslySetInnerHTML` | XSS 安全风险 |
| R-10 | 禁止在前端代码中暴露后端配置信息 | 安全风险 |

### 9.2 必须行为清单

| 编号 | 必须行为 | 说明 |
|------|----------|------|
| M-01 | 新增功能必须同步编写单元测试 | 保证可测试性 |
| M-02 | 每个文件头部必须有模块说明注释 | 提高可读性 |
| M-03 | 公共函数必须有入参和返回值的类型定义 | 保证类型安全 |
| M-04 | 数据库操作必须在事务中执行（涉及多表时） | 保证数据一致性 |
| M-05 | 配置项必须集中管理 | 便于环境切换 |
| M-06 | React 组件必须使用 TypeScript 定义 Props 类型 | 保证类型安全 |
| M-07 | API 请求必须通过统一的 Axios 实例发送 | 统一拦截器和错误处理 |
