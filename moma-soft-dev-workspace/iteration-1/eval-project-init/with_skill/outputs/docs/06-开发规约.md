## 2. 通用编码规范

### 2.1 命名规范

> **⚠️ AI 约束：以下命名规范是强制性的，AI 不得使用其他命名风格。**

| 元素 | 规范 | 示例 |
|------|------|------|
| 项目/仓库名 | kebab-case | `campus-market` |
| 前端文件名（组件） | PascalCase.tsx | `ProductList.tsx` |
| 前端文件名（工具/hooks） | camelCase.ts | `useAuth.ts` |
| 后端文件名 | PascalCase.java | `ProductService.java` |
| 类名 | PascalCase | `UserService`、`ProductController` |
| 函数/方法名 | camelCase | `getUserById`、`handleSubmit` |
| 变量名 | camelCase | `productList`、`isLoading` |
| 常量名 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT`、`DEFAULT_PAGE_SIZE` |
| 数据库表名 | snake_case（单数形式） | `user`、`product_image` |
| 数据库字段名 | snake_case | `student_id`、`created_at` |
| API 路径 | kebab-case | `/api/v1/pickup-points` |
| 环境变量 | UPPER_SNAKE_CASE | `DATABASE_URL`、`JWT_SECRET` |
| React 组件 Props 接口 | PascalCase + Props 后缀 | `ProductCardProps` |
| Java 枚举值 | UPPER_SNAKE_CASE | `CONDITION_NEW` |

### 2.2 代码风格

**前端（TypeScript/React）：**
- 缩进：2 空格
- 行宽限制：120 字符
- 引号：单引号（`'`）
- 分号：必须使用
- 组件：统一使用函数式组件 + Hooks
- 导出：命名导出（`export function`），避免默认导出

**后端（Java/Spring Boot）：**
- 缩进：4 空格
- 行宽限制：120 字符
- 大括号：K&R 风格（左括号不换行）
- 使用 Java Record 替代 Lombok DTO
- Controller 方法使用 `@Operation` 注解描述接口

### 2.3 注释规范

**前端：**
- 组件文件头部使用 `/** */` 注释说明组件用途
- 复杂业务逻辑使用行内注释解释
- 自定义 Hooks 使用 JSDoc 注释参数和返回值

**后端：**
- Service 类使用 Javadoc 注释说明类职责
- 公共方法使用 Javadoc 注释参数和返回值
- 复杂 SQL 或业务逻辑使用行内注释

**AI 特别约束：**
- ✅ 复杂业务逻辑必须添加注释
- ✅ 公共 API/函数必须有文档注释
- ❌ 禁止无意义的注释（如 `// 设置名字` `this.name = name`）
- ❌ 禁止注释掉的代码提交

## 3. 架构规范

### 3.1 分层职责

> **⚠️ AI 约束：严格遵守分层架构，不得跨层调用。**

| 层级 | 职责 | 可以调用 | 不可调用 |
|------|------|----------|----------|
| Controller | 接收请求、参数校验、调用Service、封装响应 | Service | Repository、其他Controller |
| Service | 业务逻辑处理、事务管理、调用Repository | Repository、其他Service | Controller |
| Repository | 数据库CRUD操作 | 无 | Controller、Service |
| DTO | 数据传输对象，Controller与Service间传递数据 | 无 | 不包含业务逻辑 |
| Entity | JPA实体类，映射数据库表 | 无 | 不包含业务逻辑 |

**前端分层：**

| 层级 | 职责 | 可以调用 | 不可调用 |
|------|------|----------|----------|
| Pages | 页面级组件，组合Components和Hooks | Components、Hooks、Store、API | 直接调用Axios |
| Components | 可复用UI组件 | Hooks | API、Store（通过Props接收数据） |
| Hooks | 自定义逻辑封装 | Store、API | Components |
| Store | 全局状态管理（Zustand） | API | Components、Pages |
| API | HTTP请求封装 | Axios实例 | 其他层 |

### 3.2 模块通信规则

- 后端模块间通过 Service 接口调用，禁止 Controller 直接调用其他模块 Repository
- 前端模块间通过 Zustand Store 共享状态，或通过 Props 传递
- WebSocket 消息通过 STOMP 协议路由，不直接操作底层 WebSocket API

## 4. 错误处理规范

> **⚠️ AI 约束：AI 编码时必须按以下规范处理错误，不得静默吞掉异常。**

### 4.1 错误处理原则

- **业务异常：** 使用自定义 `BusinessException`，包含错误码和用户友好消息
- **系统异常：** 捕获未预期异常，记录完整堆栈日志，返回通用错误响应
- **参数校验：** 使用 Bean Validation 注解，校验失败统一处理返回 400
- **前端错误：** Axios 响应拦截器统一处理，401 跳转登录页，其他错误弹出提示

### 4.2 统一异常结构

```java
public class BusinessException extends RuntimeException {
    private final int code;
    private final String message;

    public BusinessException(int code, String message) {
        super(message);
        this.code = code;
        this.message = message;
    }
}
```

### 4.3 日志规范

| 日志级别 | 使用场景 | 示例 |
|----------|----------|------|
| ERROR | 系统异常、数据库连接失败、外部服务调用失败 | `log.error("发送验证邮件失败, userId={}", userId, e)` |
| WARN | 业务异常、登录失败、权限不足 | `log.warn("用户登录失败, studentId={}", studentId)` |
| INFO | 关键业务操作（注册、交易创建/完成） | `log.info("用户注册成功, userId={}", userId)` |
| DEBUG | 开发调试信息、SQL查询参数 | `log.debug("查询商品列表, params={}", params)` |

## 5. 安全编码规范

> **⚠️ AI 约束：以下安全规范为红线，违反任一条即视为严重缺陷。**

- [ ] 所有用户输入必须校验和净化（使用 Bean Validation + 自定义校验）
- [ ] SQL 查询必须使用参数化查询（JPA 自动参数化），禁止字符串拼接 SQL
- [ ] 敏感信息（密码、JWT密钥、数据库密码）禁止硬编码，必须使用环境变量或配置文件
- [ ] 密码存储必须使用 BCrypt 加盐哈希（强度因子 10）
- [ ] API 必须有速率限制（使用 Bucket4j 或自定义拦截器实现）
- [ ] 文件上传必须校验文件类型（通过 Content-Type 和文件头魔数）和大小（≤5MB）
- [ ] XSS 防护：前端展示用户输入内容时必须转义，后端入库前校验
- [ ] CORS 配置：仅允许前端域名跨域访问
- [ ] JWT Token 中不存储敏感信息（仅存 userId 和角色）

## 6. 版本控制规范

### 6.1 分支策略

采用简化的 Git Flow：

- `main`：生产分支，始终保持可发布状态
- `develop`：开发分支，日常开发在此分支
- `feature/xxx`：功能分支，从 develop 拉取，完成后合并回 develop
- `fix/xxx`：修复分支，用于修复 bug

### 6.2 提交信息规范

> **⚠️ AI 约束：每次提交必须遵循以下格式。**

```
<type>(<scope>): <subject>

<body>

<footer>
```

**type 取值：**

| 类型 | 说明 |
|------|------|
| feat | 新功能 |
| fix | 修复缺陷 |
| docs | 文档变更 |
| style | 代码格式（不影响逻辑） |
| refactor | 重构 |
| test | 测试相关 |
| chore | 构建/工具变更 |

**scope 取值：** auth、user、product、chat、trade、review、notification、common

**示例：**
- `feat(product): 实现商品发布接口`
- `fix(auth): 修复登录失败计数未重置问题`

## 7. 依赖管理规范

- **添加新依赖前**必须确认：
  - [ ] 该依赖在技术架构文档中已列出，或已获得确认更新架构文档
  - [ ] 许可证兼容性已确认（优先选择 MIT/Apache 2.0）
  - [ ] 无已知高危漏洞
- **禁止事项：**
  - ❌ 禁止引入与已有依赖功能重复的库
  - ❌ 禁止使用已废弃（deprecated）的库
  - ❌ 禁止锁定不明确的版本范围（前端禁止 `*` 或 `latest`，后端使用固定版本号）

## 8. 测试规范

### 8.1 测试要求

- 后端 Service 层单元测试覆盖率 ≥ 80%
- Controller 层需编写集成测试覆盖核心接口
- 前端核心业务 Hooks 需编写单元测试

### 8.2 测试命名规范

**后端：**
- 测试类：`{被测类名}Test.java`，如 `ProductServiceTest.java`
- 测试方法：`should_{预期行为}_when_{条件}`，如 `should_throwException_when_productNotFound`

**前端：**
- 测试文件：`{被测文件名}.test.ts(x)`，如 `useAuth.test.ts`
- 测试描述：`describe('模块名') > it('should 预期行为 when 条件')`

### 8.3 测试目录结构

```
backend/src/test/java/com/campusmarket/
├── auth/
│   ├── controller/AuthControllerTest.java
│   └── service/AuthServiceTest.java
├── product/
│   ├── controller/ProductControllerTest.java
│   └── service/ProductServiceTest.java
├── ...

frontend/src/
├── __tests__/              # 通用测试
├── hooks/__tests__/        # Hooks 测试
├── pages/__tests__/        # 页面测试
```

## 9. AI 编码专项约束

> **以下约束专门针对 AI 代码生成场景设计，防止 AI 常见的编码偏差。**

### 9.1 禁止行为清单

| 编号 | 禁止行为 | 说明 |
|------|----------|------|
| R-01 | 禁止自行添加需求文档中未定义的功能 | 防止范围蔓延 |
| R-02 | 禁止更换技术架构文档中确定的技术栈 | 保持技术一致性 |
| R-03 | 禁止添加数据模型文档中未定义的表和字段 | 保持数据结构一致 |
| R-04 | 禁止修改 API 文档中已定义的接口契约 | 保持接口稳定 |
| R-05 | 禁止使用 `any` 类型（TypeScript 项目） | 保证类型安全 |
| R-06 | 禁止在代码中硬编码配置值 | 使用配置文件/环境变量 |
| R-07 | 禁止忽略错误处理 | 所有错误必须捕获和处理 |
| R-08 | 禁止生成占位符代码（如 `// TODO: implement`） | 必须实现完整逻辑 |
| R-09 | 禁止在前端直接操作 DOM | 使用 React 声明式编程 |
| R-10 | 禁止在 Entity 中编写业务逻辑 | Entity 仅用于数据映射 |
| R-11 | 禁止使用 Lombok 注解 | 使用 Java Record 或手动编写 |

### 9.2 必须行为清单

| 编号 | 必须行为 | 说明 |
|------|----------|------|
| M-01 | 新增功能必须同步编写单元测试 | 保证可测试性 |
| M-02 | 每个文件头部必须有模块说明注释 | 提高可读性 |
| M-03 | 公共函数必须有入参和返回值的类型定义 | 保证类型安全 |
| M-04 | 数据库操作必须在事务中执行（涉及多表时） | 保证数据一致性 |
| M-05 | 配置项必须集中管理（application.yml / .env） | 便于环境切换 |
| M-06 | 前端组件必须处理 loading、error、empty 三种状态 | 提升用户体验 |
| M-07 | API 请求必须通过封装的 Axios 实例发送 | 统一认证和错误处理 |
| M-08 | 表单提交必须有前端校验 + 后端校验双重保障 | 防止非法数据入库 |
