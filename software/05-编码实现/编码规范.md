## 2 通用原则

### 2.1 可读性优先

- 代码首先是写给人看的，其次才是给机器执行的
- 优先选择清晰易懂的写法，避免过度炫技
- 使用有意义的命名，让代码自文档化

### 2.2 可维护性

- 模块化设计，降低耦合度，提高内聚性
- 遵循单一职责原则，每个类/函数只做一件事
- 预留合理的扩展点，但避免过度设计

### 2.3 DRY（Don't Repeat Yourself）

- 避免代码重复，将公共逻辑提取为可复用的函数或组件
- 配置信息集中管理，避免硬编码散落在各处
- 使用模板方法、策略模式等消除重复代码结构

### 2.4 KISS（Keep It Simple, Stupid）

- 选择最简单的方案解决问题
- 避免不必要的抽象层次
- 如果一段代码需要大量注释才能理解，说明它需要重构

### 2.5 SOLID 原则

| 原则 | 英文全称 | 说明 |
|------|---------|------|
| S | Single Responsibility | 单一职责：一个类只负责一项职责 |
| O | Open/Closed | 开闭原则：对扩展开放，对修改关闭 |
| L | Liskov Substitution | 里氏替换：子类必须能够替换其父类 |
| I | Interface Segregation | 接口隔离：使用多个专门的接口而非单一臃肿接口 |
| D | Dependency Inversion | 依赖倒置：依赖于抽象而非具体实现 |

## 3 命名规范

### 3.1 总体原则

- 使用有意义的英文命名，禁止使用拼音（通用缩写除外如 Beijing）
- 名称应准确反映其用途和含义
- 避免使用单字母变量名（循环变量 `i`, `j`, `k` 除外）
- 避免使用容易混淆的名称（如 `l` 与 `1`，`O` 与 `0`）

### 3.2 包/命名空间命名

- 全部小写，使用点号分隔层级
- 以公司/组织域名反转开头
- 格式：`{{组织域名反转}}.{{项目标识}}.{{模块名}}`

```
示例：com.momasoft.projectx.user
      com.momasoft.projectx.order.service
```

### 3.3 类命名

- 使用大驼峰命名法（PascalCase）
- 名词或名词短语
- 类名应体现其职责

| 类型 | 命名规则 | 示例 |
|------|---------|------|
| 普通类 | 名词，PascalCase | `UserAccount`, `OrderDetail` |
| 接口 | 形容词/名词，可加 `I` 前缀或无前缀 | `Serializable`, `IUserService` |
| 抽象类 | `Abstract` 前缀 | `AbstractValidator` |
| 异常类 | `Exception` 后缀 | `InvalidParameterException` |
| 枚举类 | 名词，PascalCase | `OrderStatus`, `UserRole` |
| 工具类 | `Utils` 或 `Helper` 后缀 | `StringUtils`, `DateHelper` |
| 测试类 | 被测类名 + `Test` 后缀 | `UserServiceTest` |
| 数据传输对象 | `DTO` 后缀 | `UserDTO`, `OrderResponseDTO` |
| 值对象 | `VO` 后缀 | `UserVO` |
| 数据访问对象 | `DAO`/`Repository` 后缀 | `UserDAO`, `UserRepository` |

### 3.4 方法/函数命名

- 使用小驼峰命名法（camelCase）
- 动词或动词短语开头
- 布尔返回值方法使用 `is`/`has`/`can`/`should` 前缀

| 类型 | 前缀 | 示例 |
|------|------|------|
| 获取数据 | `get` / `find` / `query` | `getUserById`, `findActiveOrders` |
| 设置数据 | `set` / `update` | `setUserName`, `updateStatus` |
| 判断布尔 | `is` / `has` / `can` | `isValid`, `hasPermission`, `canDelete` |
| 创建对象 | `create` / `build` / `generate` | `createOrder`, `buildReport` |
| 删除数据 | `delete` / `remove` | `deleteUser`, `removeItem` |
| 转换数据 | `to` / `convert` / `parse` | `toString`, `convertToDTO` |
| 校验数据 | `validate` / `check` / `verify` | `validateInput`, `checkPermission` |
| 回调/事件 | `on` / `handle` | `onUserLogin`, `handleError` |

### 3.5 变量命名

- 使用小驼峰命名法（camelCase）
- 名称应能体现变量的含义和数据类型
- 集合类型使用复数形式或加 `List`/`Map`/`Set` 后缀

```
示例：
  userName          // 用户名
  orderCount        // 订单数量
  activeUsers       // 活跃用户集合
  userMap           // 用户映射
  isEnabled         // 布尔变量
  maxRetryCount     // 最大重试次数
```

### 3.6 常量命名

- 全部大写，单词间用下划线分隔（UPPER_SNAKE_CASE）
- 语义明确，避免魔法数字/魔法字符串

```
示例：
  MAX_RETRY_COUNT = 3
  DEFAULT_PAGE_SIZE = 20
  API_BASE_URL = "https://api.example.com"
  DATE_FORMAT_PATTERN = "yyyy-MM-dd HH:mm:ss"
```

### 3.7 数据库相关命名

| 对象 | 规则 | 示例 |
|------|------|------|
| 表名 | 小写，下划线分隔，加业务前缀 | `sys_user`, `biz_order` |
| 字段名 | 小写，下划线分隔 | `user_name`, `create_time` |
| 主键 | `id` 或 `表名_id` | `id`, `user_id` |
| 外键 | 关联表名 + `_id` | `order_id`, `dept_id` |
| 索引 | `idx_表名_字段名` | `idx_user_email` |
| 唯一索引 | `uk_表名_字段名` | `uk_user_phone` |
| 存储过程 | `sp_` 前缀 | `sp_calculate_salary` |
| 视图 | `v_` 前缀 | `v_user_detail` |
| 触发器 | `tr_` 前缀 | `tr_order_after_insert` |

### 3.8 文件命名

| 文件类型 | 规则 | 示例 |
|----------|------|------|
| Java/C# 类文件 | 与类名一致（PascalCase） | `UserService.java` |
| 前端组件 | PascalCase 或 kebab-case | `UserProfile.vue`, `user-profile.tsx` |
| 样式文件 | kebab-case | `main-layout.css` |
| 配置文件 | kebab-case | `app-config.yml` |
| SQL 脚本 | 版本号 + 描述 | `V1.0.1__add_user_table.sql` |
| 测试文件 | 被测文件名 + `.test`/`.spec` | `UserService.test.js` |

## 4 代码格式化

### 4.1 缩进

- 使用**空格**进行缩进，禁止使用 Tab 字符
- 缩进层级：{{缩进空格数}} 个空格（推荐 2 或 4 个）
- 连续行对齐缩进：在上一行基础上增加一级缩进

### 4.2 行长度

- 单行代码最大长度：**{{最大行长度}}** 个字符（推荐 120 字符）
- 超过最大长度时必须换行
- 换行规则：
  - 在运算符之前换行
  - 在逗号之后换行
  - 在括号内换行时增加一级缩进
  - 链式调用每个方法单独一行

### 4.3 花括号放置

- 采用 [待定]（K&R 风格 / Allman 风格）

**K&R 风格（推荐用于 Java/JavaScript/Go）：**
```
if (condition) {
    // 代码块
} else {
    // 代码块
}
```

**Allman 风格（推荐用于 C#）：**
```
if (condition)
{
    // 代码块
}
else
{
    // 代码块
}
```

### 4.4 空行规范

- 类的不同成员之间（字段、构造函数、方法）：空一行
- 方法内逻辑分组之间：空一行
- `import`/`using` 语句分组之间：空一行
- 文件末尾保留一个空行
- 禁止出现连续两个以上空行

### 4.5 空格规范

- 关键字与左括号之间加空格：`if (`, `for (`, `while (`
- 方法名与左括号之间不加空格：`method()`
- 运算符两侧加空格：`a + b`, `x = 1`
- 逗号后加空格：`method(a, b, c)`
- 冒号前后加空格（视语言而定）

## 5 注释规范

### 5.1 总体原则

- 注释应解释"为什么"而非"做了什么"
- 好的代码应当自文档化，注释是补充而非替代
- 保持注释与代码同步更新，过时的注释比没有注释更有害
- 使用中文或英文注释保持一致，本项目统一使用 [待定]

### 5.2 文件头注释

每个源代码文件应包含文件头注释，说明文件的基本信息：

```
/**
 * 文件名：{{文件名}}
 * 描述：{{文件功能描述}}
 * 作者：{{作者}}
 * 创建日期：{{创建日期}}
 * 版权所有：{{版权信息}}
 */
```

### 5.3 类注释

```
/**
 * {{类的功能简述}}
 *
 * {{类的详细描述，包括设计意图、使用场景、注意事项等}}
 *
 * @author {{作者}}
 * @since {{版本号}}
 * @see {{关联类引用}}
 */
```

### 5.4 方法注释

```
/**
 * {{方法功能简述}}
 *
 * {{方法的详细描述，包括算法说明、业务逻辑说明等}}
 *
 * @param paramName {{参数说明}}
 * @return {{返回值说明}}
 * @throws ExceptionType {{异常说明}}
 */
```

### 5.5 行内注释

- 用于解释复杂的业务逻辑或算法
- 放置在代码行上方，与代码保持相同缩进
- 避免在代码行末添加过长注释

```
// 根据用户信用评分计算折扣比例
// 评分 >= 800: 15% 折扣；评分 >= 600: 10% 折扣；其他: 无折扣
double discount = calculateDiscount(creditScore);
```

### 5.6 TODO / FIXME 约定

| 标记 | 用途 | 格式 |
|------|------|------|
| `TODO` | 待实现的功能或待优化的代码 | `// TODO({{责任人}}): {{描述}} [{{目标日期}}]` |
| `FIXME` | 已知的缺陷，需要修复 | `// FIXME({{责任人}}): {{描述}} [{{优先级}}]` |
| `HACK` | 临时解决方案，需后续重构 | `// HACK: {{原因说明}}` |
| `NOTE` | 需要注意的重要信息 | `// NOTE: {{说明内容}}` |
| `DEPRECATED` | 即将废弃的代码 | `// DEPRECATED: 使用 {{替代方案}} 代替` |

## 6 编程实践

### 6.1 错误与异常处理

- **不要吞掉异常**：捕获异常后必须进行处理（记录日志、转换抛出、补偿操作）
- **精确捕获**：优先捕获具体异常类型，避免捕获 `Exception` / `Throwable` 等通用基类
- **尽早失败**：在方法入口处进行参数校验，不满足时立即抛出异常
- **统一异常处理**：通过全局异常处理器统一处理未捕获的异常
- **自定义业务异常**：为业务错误定义专门的异常类，包含错误码和错误消息
- **异常信息完整**：异常消息应包含足够的上下文信息，便于定位问题

```
// ✗ 错误示例：吞掉异常
try {
    processOrder(order);
} catch (Exception e) {
    // 什么都不做
}

// ✓ 正确示例
try {
    processOrder(order);
} catch (OrderProcessException e) {
    logger.error("订单处理失败, orderId={}, reason={}", order.getId(), e.getMessage(), e);
    throw new BusinessException(ErrorCode.ORDER_PROCESS_FAILED, e);
}
```

### 6.2 空值安全

- 方法返回值避免返回 `null`，优先使用 Optional / 空集合 / 空字符串
- 使用对象前必须进行非空判断
- 在接口契约中明确标注是否允许传入/返回 `null`
- 使用语言提供的空安全特性（如 Kotlin 的 `?`，C# 的 `?.`）

### 6.3 输入验证

- **所有外部输入必须校验**：包括用户输入、API 请求参数、文件上传、配置读取
- 使用白名单策略而非黑名单
- 对输入的类型、长度、范围、格式进行严格校验
- 在系统边界层进行输入验证，内部方法可基于契约信任入参

### 6.4 资源管理

- 使用 try-with-resources（Java）/ using（C#）/ defer（Go）/ context manager（Python）确保资源释放
- 数据库连接、文件流、网络连接等必须在 finally 块或等效机制中关闭
- 连接池化管理，避免频繁创建/销毁连接
- 避免在循环中创建资源对象

### 6.5 线程安全

- 明确标注类的线程安全性
- 共享可变状态必须同步访问
- 优先使用不可变对象
- 使用并发集合替代手动同步的普通集合
- 避免在同步代码块中执行耗时操作
- 使用线程池替代手动创建线程

### 6.6 日志规范

| 级别 | 用途 | 示例场景 |
|------|------|---------|
| `ERROR` | 系统错误，需要立即关注 | 数据库连接失败、外部服务调用异常 |
| `WARN` | 潜在问题，不影响核心功能 | 配置缺失使用默认值、重试操作 |
| `INFO` | 关键业务流程节点 | 用户登录、订单创建、支付完成 |
| `DEBUG` | 调试信息 | 方法入参出参、中间变量值 |
| `TRACE` | 更细粒度的调试 | 循环迭代详情、第三方库调试 |

**日志规范要求：**

- 禁止使用 `System.out.println` / `console.log`（生产代码中）进行日志输出
- 使用参数化日志，避免字符串拼接：`logger.info("用户 {} 登录成功", userId)`
- 敏感信息脱敏后再记录日志
- 异常日志必须包含完整堆栈信息
- 日志内容应包含足够的上下文信息（请求 ID、用户 ID、业务 ID 等）

## 7 安全编码规范

### 7.1 SQL 注入防护

- **强制使用参数化查询**，禁止拼接 SQL
- 使用 ORM 框架的安全查询方式
- 对动态表名/列名进行白名单校验
- 数据库账户遵循最小权限原则

```
// ✗ 危险：SQL 拼接
String sql = "SELECT * FROM user WHERE name = '" + userName + "'";

// ✓ 安全：参数化查询
String sql = "SELECT * FROM user WHERE name = ?";
preparedStatement.setString(1, userName);
```

### 7.2 XSS 防护

- 所有输出到页面的用户输入必须进行 HTML 转义
- 使用框架提供的模板引擎自动转义功能
- 设置 Content-Security-Policy 响应头
- Cookie 设置 HttpOnly 和 Secure 属性

### 7.3 敏感数据处理

- 密码必须使用安全的哈希算法（如 bcrypt、scrypt、Argon2）加盐存储
- 敏感配置信息（数据库密码、API Key 等）不得硬编码在源码中
- 使用环境变量或加密配置中心管理敏感信息
- 日志中禁止记录明文密码、完整身份证号、完整银行卡号等敏感信息
- 传输敏感数据必须使用 HTTPS/TLS

### 7.4 认证与授权

- 使用成熟的认证框架，避免自行实现认证逻辑
- 实施最小权限原则
- 关键操作需要二次验证
- Token/Session 设置合理的过期时间
- 登录失败实施速率限制，防止暴力破解

## 8 版本控制规范

### 8.1 分支命名规范

| 分支类型 | 命名规则 | 示例 |
|----------|---------|------|
| 主分支 | `main` / `master` | `main` |
| 开发分支 | `develop` | `develop` |
| 功能分支 | `feature/{{功能描述}}` | `feature/user-login` |
| 修复分支 | `bugfix/{{缺陷编号}}-{{描述}}` | `bugfix/BUG-123-fix-null-pointer` |
| 热修复分支 | `hotfix/{{描述}}` | `hotfix/payment-timeout` |
| 发布分支 | `release/{{版本号}}` | `release/v1.2.0` |

### 8.2 提交信息格式

采用 Conventional Commits 规范：

```
<type>(<scope>): <subject>

<body>

<footer>
```

**type 类型：**

| 类型 | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档变更 |
| `style` | 代码格式调整（不影响功能） |
| `refactor` | 重构（既不修复缺陷也不添加功能） |
| `perf` | 性能优化 |
| `test` | 添加或修改测试 |
| `chore` | 构建/工具变更 |
| `ci` | CI 配置变更 |

**示例：**
```
feat(user): 添加用户注册功能

- 实现用户注册接口
- 添加邮箱验证功能
- 添加注册参数校验

Closes #123
```

### 8.3 代码审查流程

1. 开发者完成编码后，提交 PR/MR 至目标分支
2. 至少 {{最少审查人数}} 名审查人员进行代码审查
3. 审查人员按照审查清单逐项检查
4. 发现问题通过评论反馈，标注严重程度
5. 开发者修复问题后更新 PR
6. 所有问题关闭后，审查人员批准合并
7. 合并后删除功能分支

### 10.3 IDE 配置

为保证团队成员的开发环境一致，项目应提供统一的 IDE 配置文件：

- **EditorConfig**：提交 `.editorconfig` 文件至版本库，统一基础编辑器设置
- **IDE 设置共享**：将 IDE 格式化/检查配置导出并存放在版本库中

```ini
# .editorconfig 参考配置
root = true

[*]
charset = utf-8
end_of_line = lf
indent_style = space
indent_size = {{缩进空格数}}
insert_final_newline = true
trim_trailing_whitespace = true
max_line_length = {{最大行长度}}
```
