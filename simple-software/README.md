# AI 驱动的简化软件开发文档体系

## 一、概述

本文档体系专为 **AI 驱动的快速软件开发** 设计。核心理念是：

> **用户只需输入需求 → AI 按顺序生成约束文档 → 文档反过来约束 AI 的编码行为**

与传统软件工程文档不同，本体系的每份文档都包含明确的 **"⚠️ AI 约束"** 标记，这些约束作为 AI 编码时的"护栏"，防止 AI 在开发过程中偏离需求、自行发挥或技术栈漂移。

## 三、文档生成流程与使用节点

### 整体流程图

```
用户输入需求
     │
     ▼
┌─────────────────┐
│ 阶段1: 需求定义    │   用户审核 ✅
│  01-项目概要       │◄──────────┐
│  02-产品需求文档   │           │
└────────┬────────┘           │  不通过则修改
         │ 通过                 │
         ▼                     │
┌─────────────────┐           │
│ 阶段2: 技术设计    │   用户审核 ✅
│  03-技术架构文档   │◄──────────┤
│  04-数据模型文档   │           │
│  05-API接口文档    │           │
└────────┬────────┘           │
         │ 通过                 │
         ▼                     │
┌─────────────────┐           │
│ 阶段3: 开发约束    │   用户审核 ✅
│  06-开发规约       │◄──────────┘
│  07-测试策略       │
└────────┬────────┘
         │ 通过
         ▼
┌─────────────────┐
│ 阶段4: AI 编码     │  ── 参照 01~07 全部文档
│ （受文档约束）      │
└────────┬────────┘
         │ 持续记录
         ▼
┌─────────────────┐
│ 08-变更日志       │  ── 贯穿全流程
└─────────────────┘
```

### 各阶段详细说明

#### 阶段 1：需求定义

| 节点 | 使用方式 |
|------|----------|
| **触发条件** | 用户提供任意形式的需求描述（文字、语音转文字、草图描述等） |
| **AI 操作** | 1. 解读用户需求，生成 `01-项目概要.md`<br>2. 用户确认后，展开生成 `02-产品需求文档.md` |
| **用户操作** | 审核项目范围是否正确，特别关注"明确不做的事项"部分 |
| **通过标准** | 用户确认项目目标、功能范围、验收标准无误 |

#### 阶段 2：技术设计

| 节点 | 使用方式 |
|------|----------|
| **触发条件** | 阶段 1 文档审核通过 |
| **AI 操作** | 基于需求文档 + 用户技术倾向，生成 `03`、`04`、`05` 三份文档（可并行） |
| **用户操作** | 审核技术选型是否合理，数据结构是否完整，接口设计是否满足需求 |
| **通过标准** | 用户确认技术栈、数据模型、API 设计无误 |

#### 阶段 3：开发约束

| 节点 | 使用方式 |
|------|----------|
| **触发条件** | 技术架构确认后 |
| **AI 操作** | 生成 `06-开发规约.md` 和 `07-测试策略.md` |
| **用户操作** | 审核编码规范和测试要求，可补充自定义规则 |
| **通过标准** | 用户确认开发约束和测试标准 |

#### 阶段 4：AI 编码

| 节点 | 使用方式 |
|------|----------|
| **触发条件** | 所有约束文档就绪 |
| **AI 操作** | 将 01~07 文档作为上下文，开始编码实现 |
| **约束执行** | AI 编码时严格遵循各文档中的"⚠️ AI 约束"标记 |
| **变更管理** | 如需偏离文档，先在 `08-变更日志.md` 登记，获得确认后再执行 |

## 四、文档间依赖关系

```
01-项目概要
 ├──▶ 02-产品需求文档
 │     ├──▶ 04-数据模型文档（数据需求 → 表结构）
 │     ├──▶ 05-API接口文档（功能需求 → 接口定义）
 │     └──▶ 07-测试策略（功能需求 → 测试用例）
 └──▶ 03-技术架构文档
       ├──▶ 04-数据模型文档（技术选型 → 数据库方案）
       ├──▶ 05-API接口文档（架构风格 → 接口规范）
       └──▶ 06-开发规约（架构约束 → 编码规范）

08-变更日志 ◀── 记录对以上所有文档的变更
```

**依赖规则说明：**

| 关系 | 说明 |
|------|------|
| 01 → 02 | 项目概要定义范围，需求文档展开细节 |
| 01 → 03 | 项目概要中的技术倾向，指导架构选型 |
| 02 → 04 | 需求中的数据实体，映射为数据库表结构 |
| 02 → 05 | 需求中的功能点，映射为 API 接口 |
| 02 → 07 | 需求中的验收条件，映射为测试用例 |
| 03 → 04 | 技术架构决定数据库类型和存储方案 |
| 03 → 05 | 架构风格决定接口规范（如 RESTful 约定） |
| 03 → 06 | 技术栈决定编码规范（语言风格、框架约定） |
| 08 ← 全部 | 任何文档的变更都必须在变更日志中记录 |

## 五、占位符标记规范

所有模板使用统一的标记系统，便于 AI 识别和填写：

| 标记格式 | 含义 | 示例 |
|----------|------|------|
| `{{变量名}}` | 需要填写的具体值 | `{{项目名称}}` |
| `<!-- AI_FILL: 说明 -->` | AI 根据上下文自动生成的内容块 | `<!-- AI_FILL: 根据需求生成 -->` |
| `<!-- REPEAT_START -->` ... `<!-- REPEAT_END -->` | 可重复的结构块（根据实际数量复制） | 多个表、多个接口 |
| `[待定]` | 需要用户手动决策的内容 | 技术选型偏好 |
| `<!-- OPTIONAL_START -->` ... `<!-- OPTIONAL_END -->` | 可选内容（根据项目规模裁剪） | WebSocket、缓存策略 |
| `⚠️ AI 约束` | AI 编码时必须遵守的强制约束 | 禁止使用的技术、必须遵循的格式 |
| `✅` / `❌` | 必须做 / 禁止做 | 实现边界标记 |

## 六、快速使用指南

### 对用户

1. **提供需求** — 用自然语言描述你想要的软件，越详细越好
2. **逐阶段审核** — AI 生成每个阶段的文档后，认真审核并确认
3. **重点关注** — 每份文档中的"明确不做"和"AI 约束"部分
4. **确认技术偏好** — 如果有技术栈偏好，在项目概要中明确
5. **变更管理** — 开发过程中如需修改，通过变更日志走正式流程

### 对 AI

1. **严格按顺序生成** — 遵循 阶段1 → 阶段2 → 阶段3 的顺序
2. **等待确认** — 每个阶段文档生成后，等待用户审核确认再继续
3. **约束即法律** — 编码时，文档中的"⚠️ AI 约束"具有最高优先级
4. **先登记后变更** — 需要偏离文档时，先更新变更日志，获得确认后执行
5. **可追溯** — 代码实现可以追溯到需求文档中的具体条目

## 七、与完整版文档体系的对比

| 维度 | 完整版 (`software/`) | 简化版 (`simple-software/`) |
|------|---------------------|---------------------------|
| 阶段数 | 10 个阶段 | 4 个阶段 |
| 文档数 | 30+ 份 | 8 份 |
| 适用场景 | 大型项目、合规要求高 | 快速启动、AI 驱动开发 |
| 核心目标 | 全面的过程管理 | 约束 AI、防止偏离 |
| 人工参与 | 大量人工编写和评审 | 用户只需审核确认 |
| 迭代方式 | 瀑布/V模型 | 渐进式、文档驱动 |
